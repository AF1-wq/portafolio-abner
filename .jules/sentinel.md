## 2026-11-01 - CSRF Protection for Endpoints Handling Traditional Forms
**Vulnerability:** The `/api/send-message` endpoint lacked Cross-Site Request Forgery (CSRF) protection. Normally, an API might enforce a strict `Content-Type: application/json` as partial CSRF defense, but this endpoint also accepts `application/x-www-form-urlencoded` or `multipart/form-data` to support traditional HTML form submissions.
**Learning:** Forcing strict JSON on dual-use endpoints (API + Form submission) breaks legitimate traditional form functionality. CSRF can still be effectively mitigated by relying on standard Origin or Referer header validation when requests are made by modern browsers.
**Prevention:** When an endpoint handles both JSON and standard form submissions, validate the `Origin` or `Referer` headers against the server's `request.host` instead of strictly enforcing the Content-Type.

## 2024-11-10 - CSRF Hostname Parsing Bypass via URL Credentials
**Vulnerability:** The CSRF protection in `/api/send-message` validated the origin by parsing the URL with `urllib.parse.urlparse`, extracting the `.netloc` property, and splitting by `:` to extract the hostname. This was vulnerable to a bypass if an attacker supplied an Origin header with credentials (e.g., `http://localhost:80@attacker.com`), where the resulting extracted hostname bypassed the protection by incorrectly evaluating to `localhost`.
**Learning:** Using string manipulation (e.g. `.netloc.split(':')[0]`) to extract hostnames from parsed URLs is insecure and prone to bypass attacks when the URL contains authentication credentials. The `.hostname` property provides a safer and accurate way to extract the hostname component.
**Prevention:** When comparing host headers for CSRF protection (e.g., matching Origin/Referer to request.host), always use `urllib.parse.urlparse().hostname` to safely extract the hostname instead of parsing `.netloc` directly.
